# M6 双岗位作品集发布计划

> 状态：M6-P0～P2 已完成；P3、P4 尚未开始。P1 的远程 CI 状态仍为“配置已准备、未在远程执行”。
>
> 执行原则：M6 不增加病例、模型、记忆算法、网页功能或游戏机制。任何远程创建、推送或公开发布必须在 P4 获得用户明确授权。

## 1. M6 分阶段

| 阶段 | 目标 | 主要产物 | 退出条件 | 外部动作边界 |
|---|---|---|---|---|
| P0：发布准备审计与决策 | 查清公开风险、可复现缺口和作品叙事 | 发布审计、路线图、用户决策表 | 本地证据完整；未替用户决定身份、版权或发布 | 完全离线；不创建远程 |
| P1：仓库整理、安装与 CI | 已完成：让全新环境按公开说明复现核心路径 | 双重授权、package resources、Windows 3.12 依赖快照、构建/安装验证、CI、文档索引 | 本地 wheel/sdist 与 source checkout 均工作；CI 配置不调用模型/API；远程运行待 P4 前复核 | 仅官方元数据与核心依赖下载；没有远程、推送或发布 |
| P2：项目首页与演示素材 | 已完成：让招聘者 30 秒理解、3 分钟运行或沿证据下钻 | 精简 README、英文摘要、两张 SVG、三张真实终端素材、脱敏文本、四版演示脚本 | 两个岗位入口、数字证据、本地链接、素材 SHA、隐私与版权均离线通过 | 未录制/上传视频；未创建远程 |
| P3：求职材料 | 把同一事实转化为两套诚实岗位叙事 | 两套简历要点、30 秒/3 分钟讲解、面试问答、证据链接 | 每个数字可追溯；单次案例、合成指标和工程事实明确分层 | 不投递、不发送外部消息 |
| P4：最终发布检查 | 对精确提交做发布门禁并由用户决定是否公开 | 最终审计、发布清单、候选 Tag/Release 说明 | 身份/版权/秘密/构建/CI/链接/媒体全部通过，且用户明确授权 | 只有此时才可创建远程、推送或发布 |

M6-P1 不能在用户尚未决定身份和许可证时擅自生成正式版权声明。P4 以前的所有工作默认只留在本地。

## 2. 工作优先级

### 发布前必须完成

1. 用户确认公开策略、公开身份、未来 Git 作者、历史作者处理、项目名称和许可证；
2. 明确代码、病例文本、文档、演示媒体的权利边界；
3. 选择“源码 clone 运行”还是“可独立安装 wheel”，并对所承诺形态做干净环境验证；
4. 解决 `data/cases`、`data/campaign` 等资源在安装包中的定位；
5. 让 `xuanyi-play` 在无 API Key、无 BGE/CUDA 的公开安装中可启动；
6. 建立不调用模型/API的公共 CI 和全历史敏感信息门禁；
7. 形成第三方依赖/模型许可清单；
8. P4 在精确提交上复核秘密、构建、测试、链接和工作树；
9. 获得用户对远程创建、推送和发布的单独授权。

### 推荐完成

- README 改为快速概览 + 详细索引；
- 增加 5～8 行英文摘要；
- 提供一张安全数据流架构图；
- 提供一个无 Key CLI GIF/短视频和一张三病例 Campaign 图；
- 建立 `docs/INDEX.md`，保留但分类历史停止记录与负结果；
- 区分核心依赖 constraints 与可选 Windows/CUDA 锁；
- 在 Windows 3.12 之外验证至少 Ubuntu 3.11/3.12；
- 为作品集指标建立从首页到验证记录的证据链接。

### 可选增强

- 真人配音版视频；
- Gitee 镜像；
- 公开 Issue/Project；
- Tag、Release、PyPI；
- 完整英文文档；
- macOS 兼容验证。

### 明确不做

- 为发布新增病例、玩法、模型、Prompt 或记忆算法；
- 把未过线的 semantic memory 打开或包装成成功；
- 为首页指标重跑付费实验；
- 在公共 CI 下载 BGE 或调用 DeepSeek；
- 删除负结果、停止记录或伪造玩家收益；
- 在没有授权时改写历史、创建远程、推送、Tag 或 Release。

## 3. 两类岗位的首页叙事顺序

### 3.1 Agent 应用岗入口

1. **问题**：模型擅长语言，但关键游戏状态不能交给模型直接修改；
2. **架构**：安全视图 → 结构化 `AgentAction` → 公开行动契约 → 工具/规则层 → 领域事件 → 原子保存/重放；
3. **工具证据**：9 个 MCP 工具、进程内和真实 stdio 子进程验证；
4. **可靠性证据**：拒绝零写入、跨玩家隔离、预算/超时/用量门禁、Episode/Campaign 重放；
5. **真实失败闭环**：P4b 参数错误与未闭环 → P4c 通用契约修复 → P4d 单次真实恢复；
6. **RAG 工程判断**：M4 工程闭环完成，M4.5 Dense 质量未过线，正式 Prompt 默认关闭；
7. **复现入口**：无 Key Fake/no-LLM、MCP 和测试命令；
8. **限制**：真实成功率、生产并发、远程部署和真实用户收益未验证。

这个入口优先展示系统边界和失败分析，不用世界观细节挤占首屏。

### 3.2 游戏 AI 产品岗入口

1. **体验主张**：同一玩家完成三个志怪病例，退出重启后继续，NPC 会以确定性公开事实回应前史；
2. **立即试玩**：`xuanyi-play`，无 API Key、无 GPU；
3. **内容证据**：三案、多种调查顺序、resolved/suppressed/worsened 三类结局；
4. **连续性**：两项知识成长、两处历史反应、推荐顺序但不锁关；
5. **可用性**：普通用户 CLI、进度恢复、双玩家隔离、Fake 演示；
6. **产品取舍**：语义记忆没有达到召回门槛，因此正式玩法使用确定性 Campaign，而不是冒险注入 Prompt；
7. **真实模型证据**：P4b 失败和 P4d 单次恢复并列，不声称稳定成功率；
8. **限制**：没有网页/引擎界面、真实玩家研究、留存数据或生产运维。

这个入口优先展示“可玩、连续、可恢复”，Agent 实现细节通过架构链接下钻。

## 4. 首页建议结构

建议公开 README 控制为以下顺序：

1. 项目名 + 中英文一句话摘要；
2. 3 个可验证亮点：三病例纵向切片、确定性安全 Agent、真实正负实验；
3. 60 秒无 Key 启动；
4. 一张整体架构图；
5. 30 秒 GIF 或截图；
6. Agent 应用岗 / 游戏 AI 产品岗两个独立阅读入口；
7. 可复现测试和平台说明；
8. 结果边界与已知限制；
9. 详细文档索引。

历史文档不删除。建议索引分组：

- `Core architecture and decisions`：ROADMAP、ADR、M2/M3/M4/M5 exit audit；
- `Playable product`：病例设计、Campaign、Demo、M5 evidence；
- `Real model experiments`：P4b/P4c/P4d；
- `Memory/RAG research`：M4、M4.5 正负结果；
- `Historical checkpoints`：身份停止、启动停止、遥测停止和旧实验方案。

## 5. 用户决策清单

| 决策 | 推荐方案 | 替代方案 | 主要影响 | 可逆性 / 授权 |
|---|---|---|---|---|
| 仓库公开或私有 | P1/P4 门禁通过后公开 GitHub 仓库 | 先建私有仓库，仅在面试中演示 | 公开可直接验证能力；私有更保护内容但增加招聘者访问摩擦 | 公开后可能被复制，实际上不可完全撤回；必须用户授权 |
| 真实姓名或网名 | 使用与简历/GitHub一致的稳定职业身份；若隐私优先则用固定网名 | 真实姓名作为作者和版权人 | 一致身份利于归属；真实姓名提高可验证性也增加隐私暴露 | 发布前易改，发布后难完全收回 |
| 未来 Git 作者 | 用户确认后只配置本仓库的公开名与 noreply/职业邮箱 | 继续 `wyd@localhost` | 影响未来提交归属与平台关联 | 对未来提交可逆；不得在 P0 改 Git 配置 |
| 是否改写既有作者 | **建议不改写**，保留 52 个哈希和审计链，并说明 `wyd` 是开发期署名 | 在首次公开前重写全部历史并同步所有哈希证据 | 改写会改变全部提交、破坏文档引用并增加审计成本 | 高风险；公开后不可安全撤销；必须专项授权 |
| 公开项目名称 | “玄医问道：可审计的师承型智能 NPC”，配英文短名 | 保留“玄医师承型智能 NPC” | 影响仓库 URL、README、简历一致性 | 创建远程前易改；需用户确认 |
| 代码许可证 | 代码单独采用明确 OSI 许可证；默认建议评估 Apache-2.0 | MIT；或暂不开放复用 | Apache-2.0 权利和专利条款更完整；MIT 更简洁 | 发布许可证后通常不能撤销既有版本授权；需用户/法律判断 |
| 病例与文档授权 | 与代码分离；默认建议保留病例商业复用权，再决定 All Rights Reserved 或内容许可证 | CC BY 4.0；若接受非商业复用可评估 CC BY-NC 4.0 | 决定他人能否复制世界观、病例和文案 | 已授权副本通常不可收回；必须用户决定 |
| 英文摘要 | 增加 5～8 行英文摘要和英文关键词 | 全中文；或完整双语 | 提高国际团队可读性，成本低 | 可逆；推荐 P2 完成 |
| 发布平台 | GitHub 作为主仓库 | 私有 GitHub；之后按需增加 Gitee 镜像 | GitHub 更利于求职验证；镜像增加维护成本 | 创建/公开均需 P4 明确授权 |
| 真人声音 | 首版不使用真人声音，采用字幕/终端解说 | 真人配音；合成配音 | 无配音更保护隐私、迭代快；真人声音更有亲和力 | 上传后难完全撤回；录制/发布分别授权 |
| 是否展示模型与费用 | 在实验证据页公开模型名和脱敏成本，同时强调单次案例 | 首页不展示，只在面试口述；或仅展示模型不展示成本 | 透明成本有 Agent 工程价值，但不能包装成成功率 | 文档可改，外部缓存不可控；不公开请求 ID |
| 实验文档范围 | 全部保留在主分支，用精简 README + `docs/INDEX.md` 导航 | 建立精简展示分支 | 保留负结果最可信；展示分支会产生双轨维护和证据漂移 | 导航可逆；不建议长期分叉 |
| 公开 Issue/看板 | 初次发布不创建，稳定后只建 3～5 个真实后续项 | 立即公开 Roadmap/Issues | 精简仓库更聚焦；看板可展示产品意识但需持续维护 | 可逆，但所有外部写入需授权 |

### 建议用户先回答的最小集合

进入 M6-P1 前，至少需要用户确认：

1. 公开还是私有，以及预期平台；
2. 公开身份和未来提交邮箱；
3. 是否保留 `wyd@localhost` 历史；
4. 项目公开名称；
5. 代码许可证；
6. 病例文本和文档是否允许他人复用。

其他选择可以在 P2/P3 再决定，不阻塞 P1 的纯工程整理。

## 6. P1 建议任务包

在用户作出上述决策后，P1 建议按以下顺序执行：

1. 写入确认后的作者、许可证、URL 占位和分类元数据；
2. 增加第三方许可证/归属清单，联网核验部分另设授权门禁；
3. 强化 `.gitignore` 和禁止跟踪测试；
4. 决定 package data 方案，消除 CLI 对源码仓库根目录的隐式依赖；
5. 生成核心 constraints/锁定方案，不把 CUDA 依赖拉入基础安装；
6. 构建 wheel/sdist，并在全新临时环境从产物安装；
7. 验证 `xuanyi-play`、`xuanyi-mcp-stdio`、核心验收和 Demo；
8. 建立 Windows 3.12 + Ubuntu 3.11/3.12 的无模型/API CI；
9. 创建 `docs/INDEX.md`，但把首页视觉与演示素材留到 P2；
10. 输出 P1 精确复现报告，不创建远程。

## 7. 结果表述边界

公开材料可以写：

> 完成了三个病例、确定性跨案连续性、结构化 Agent 工具、MCP、拒绝恢复、持久化重放和普通用户 CLI 的本地游戏 AI 纵向切片，并保留真实模型正负案例和语义检索未过线的负结果。

公开材料不得写：

- 真实模型已具有稳定成功率；
- 合成 Gold 等于产品准确率或玩家收益；
- semantic memory 已进入正式玩法；
- 已达到生产级并发、远程部署或商业游戏质量；
- Windows 单机证据等于全平台兼容。
